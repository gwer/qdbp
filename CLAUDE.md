# qdbp.net — инструкции для агента

Статический мультиязычный сайт браузерных инструментов и калькуляторов. Монетизация — реклама, трафик — SEO.
Общаемся на русском. Исходный контент инструментов пишется на русском.

## С чего начать сессию
- `docs/README.md` — карта документов и главные выводы; `docs/02-roadmap.md` — что сделано и что дальше (отметки по фазам).
- `docs/03-tech.md` — архитектура и принятые решения (раздел 13 — что сознательно НЕ делаем). Перед архитектурными изменениями сверяться с ним, после — обновлять.
- `docs/04-catalog.md` — какие инструменты делать и в каком порядке (ценность × сложность).
- Документы — живые черновики для обсуждения: решения в них меняются по итогам разговора, правь их, когда решение изменилось.

## Команды
- `pnpm dev` / `pnpm build` / `pnpm test`
- `pnpm check` — типы, тесты, сборка, пост-проверки `dist/`. Должен быть зелёным, прежде чем говорить «готово».
- `pnpm urls:update` — подтвердить изменения списка URL в `urls.txt` (только когда появление/удаление страниц намеренное).

## Структура (подробно — docs/03-tech.md, разделы 3–5)
- `src/pages/[lang]/{category}/{tool}/` — папка = URL. `index.astro` — одинаковый у всех инструментов (копировать как есть); всё своё — в `_tool/`: `tool.ts` (`export const def = defineCalculator|defineTool(...)`, `export default island(def)`), тесты, код, `i18n/{lang}.json`, `content/{lang}.md`.
- `src/pages/[lang]/{category}/` — `index.astro` (одинаковый у всех категорий) + `_category/` (`category.ts`, `i18n/{lang}.json`).
- Общая обвязка страниц — `src/layouts/ToolPage.astro`, `CategoryPage.astro`, `Base.astro`. Каталог и все проверки файлов — `src/lib/catalog.ts`, `src/lib/validate.ts`.
- Языки сайта — `src/i18n/config.ts` (`SITE_LANGS`); общие строки — `src/i18n/ui/{lang}.json`.

## Правила, которые легко нарушить
- Только клиентская логика, никакого сервера. Без инструментов на часто меняющихся данных (курсы, ставки «на сегодня»): такое значение — поле ввода.
- Язык у инструмента включён, если есть и `i18n/{lang}.json`, и `content/{lang}.md`. Наборы ключей во всех языках одного инструмента одинаковые.
- Слаги английские на всех языках; URL после публикации не меняются без редиректа в `public/_redirects`.
- Числа: поля `type="text"`, разбор — `parseNumber(input, lang)`, вывод — только через `src/lib/format.ts`. Деньги — `decimal.js-light`. Ничего, зависящего от «сегодня», при сборке не считать (сборка в UTC).
- Время на часах — только через поле `type: 'time'` движка (своё текстовое поле, не нативный `<input type="time">`): формат 12/24 ч выбирает пользователь (по умолчанию — по языку: en — 12 ч), выбор запоминается на весь сайт и применяется ко всем результатам со временем. Нативный time input не использовать нигде: его формат диктует система.
- Даты — так же: поле `type: 'date'` движка или `src/ui/DateField.tsx` в своих компонентах (текст в записи языка + кнопка календаря). Нативный `<input type="date">` напрямую не использовать: его формат тоже диктует система.
- Физические величины (длина, площадь, объём, масса, расход) — поле/результат `type: 'quantity'` с `unit` и, где это нужно американцам, `imperial` (+ `defaultImperial` с «круглым» значением); подписи — без единиц, единицу показывает суффикс. Подробно — docs/03-tech.md, 6.5.
- Значения по умолчанию, зависящие от рынка (ставка НДС, формат кирпича, суммы в примерах), — через `byLang` в описании поля, а не своими обёртками.
- Порядок инструментов в списках задаётся `order` в `tool.ts` (меньше — выше), не алфавитом.
- Если отрицательные значения не нужны — ставить `min: 0` (это и проверка, и цифровая клавиатура на телефоне).
- Формулы — тесты с эталонами из независимого источника. Цифры в примерах `content/*.md` сверять с реальным расчётом.
- **Заголовки инструментов — существительные, а не глаголы и не обрубки фраз.** `title` = название инструмента («Калькулятор дней», «Кредитный калькулятор», «Конвертер Unix timestamp», «Счётчик слов и символов»), при необходимости — двоеточие и уточнение, на какой вопрос он отвечает: «Калькулятор дней: сколько дней между датами». Глаголы и сценарии («прибавить», «вычесть», «сколько будет через…») — в `description`, FAQ и тексте. Часть до двоеточия — короткое имя (хлебные крошки, списки, ссылки в тексте других страниц), полный `title` — H1 и `<title>`. Так же на всех языках («Calculadora de días: …», «Tagerechner: …»).
- Переводы: не дословно, а с адаптацией (местная валюта, реалии, термины рынка — Price/SAC в pt, sistema francés в es и т. п.).
- Предпочитать стандартные механизмы Astro/Preact своим, даже ценой небольшого шаблонного кода. Минимум абстракций: новое общее — только когда понадобилось второй-третий раз.
- Версии зависимостей — выпущенные не меньше двух недель назад.
- Не обещать молча: если цель недостижима (лимит размера файла, вычет, точность), сказать об этом у результата, а не отдавать «лучшее, что вышло», как успех. Текст статьи — ровно про то, что делает код.
- Быстрый путь в расчёте (прыжок неделями, двоичный поиск, формула вместо цикла) — только с тестом-сверкой против простой пошаговой реализации на всех краевых стартах. Двоичный поиск — только по монотонной функции; вычеты и пороги монотонность ломают.
- Интерактив с задержкой (таймеры, анимация, звук, async): при смене ввода и размонтировании — отменять; индексы и выборы, зависящие от данных (подсказка графика, выбранный префикс), проверять при смене данных, видимое и применённое значение должны совпадать.
- Параметры из URL — как ввод пользователя: пустая строка и пробелы — не 0, `Infinity`/`1e309` — не число; некорректное не применять.
- Медицинские, юридические и налоговые утверждения — по первоисточнику (ФНС, ACOG и т. п.), не по памяти; если не проверено — так и написать в отчёте пользователю, не в тексте сайта.

## Проверка изменений в UI
Браузерные скрипты прошлых проверок лежат в scratchpad сессии и не переживают её; для регрессии после изменений движка достаточно smoke-прохода по всем URL из `urls.txt` (страница открывается, нет ошибок в консоли, у калькуляторов есть результат).

Юнит-тестов для интерфейса нет. После изменений в UI — проверить в браузере не только открытую страницу, но и состояния после действий (загруженные файлы, раскрытые блоки, выбранные режимы, длинные подписи других языков). Переполнение на телефоне мерить относительно заданной ширины viewport (320/375 px) — мобильный Chrome расширяет `innerWidth` вместе с переполнением, и проверка `scrollWidth > innerWidth` его не видит. Широкие таблицы — в `.table-wrap`, длинные подписи — `table.wrap`, главная колонка — ближе к началу. Проверять в браузере: в системе есть `/usr/bin/google-chrome`; `playwright-core` ставить во временную папку (scratchpad), не в проект. Сайт локально — `pnpm build && pnpm preview` (preview запускается как демон, останавливать `pnpm exec astro preview stop`). Порт по умолчанию 4321, но у пользователя там часто запущен `pnpm dev` — тогда preview уходит на 4322; проверять порт (`ss -ltnp | grep 432`) и тестировать именно preview, а не dev-сервер (dev даёт ложные ошибки вроде `504 Outdated Optimize Dep`). Чужие процессы не останавливать.

## Работа с пользователем
- Коммитить, когда работа завершена (`pnpm check` зелёный): проверку и коммит связывать через `&&`, не `;`. В коммит — только свои изменения: перед `git add` смотреть `git status`; отчёты и скрипты ревьюера (`docs/reviews/`) — отдельным коммитом. Не коммитить, если не уверен в результате, если нужна проверка пользователем или если он просит не коммитить. Большую работу по этапам — коммитом на каждый завершённый этап. Push в `main` — только по просьбе: Cloudflare сразу деплоит.
- Если просят «объясни» или «ничего не меняй» — сначала объяснение, без правок.
- Пользователь чувствителен к оверинжинирингу: предлагать минимальное решение, всё «на будущее» явно откладывать.
- Рекомендации — с проверкой фактами (замер, сборка, документация), а не по памяти; если не проверено — так и сказать.
