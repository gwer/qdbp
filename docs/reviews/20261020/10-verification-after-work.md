## V01 — P1. JPEG-комментарии после первого скана всё ещё попадают в скачанный файл

**Статус прежнего F02: исправлен исходный пример, но не весь класс проблемы.** Общая функция удаления JPEG-метаданных используется и компрессором, и EXIF-инструментом.

Код: [остановка разбора на SOS](</home/gwer/code/qdbp/src/ui/files/jpeg.ts:26>), [копирование оставшейся части файла без разбора](</home/gwer/code/qdbp/src/ui/files/jpeg.ts:216>), [возврат очищенного оригинала в компрессоре](</home/gwer/code/qdbp/src/pages/[lang]/images/compress-image/_tool/CompressImage.tsx:23>).

Воспроизведение:

1. Взять [тестовый JPEG](evidence/recheck/evidence/after-scan-private-comment.jpg): обычное изображение 800×600, приватный COM-комментарий `RECHECK_PRIVATE_AFTER_SCAN` расположен перед EOI, после данных первого скана. Есть и исходный комментарий до SOS для контроля.
2. Открыть `/ru/images/compress-image/`, загрузить файл с настройками по умолчанию и скачать результат. Сжатие невыгодно, выбирается исходное изображение после `stripJpeg`.
3. В [скачанном JPEG](evidence/recheck/evidence/after-scan-downloaded.jpg) исходный комментарий до SOS удалён, но `RECHECK_PRIVATE_AFTER_SCAN` сохранён. Вход — 7824 байта, выход — 7799. Скачанный результат декодируется браузером как 800×600.
4. Открыть `/ru/images/exif/` и повторить удаление метаданных: [результат EXIF](evidence/recheck/evidence/after-scan-exif-downloaded.jpg) также сохраняет этот комментарий.

Причина: `segments()` возвращает только сегменты до первого SOS, а `stripJpeg()` копирует `b.subarray(sos)` целиком. Метаданные в этой части не рассматриваются. Это не проблема загрузки на сервер: утечка остаётся **в скачанном файле**, вопреки обещанию удаления.

Минимальное направление исправления: не считать просмотр заголовка до первого SOS полной очисткой. Либо корректно разбирать последующие маркеры/сканы, либо для случаев, где очистка оригинала не гарантирована, отдавать перекодированный результат. Сохранение ориентации и допустимого ICC не должно зависеть от сохранения остальных приватных блоков.

Приёмка: оба приложенных браузерных сценария проходят; комментарии до и после скана отсутствуют в результате, картинка декодируется, ориентация не ломается. Добавить отдельный эталон для многосканового JPEG. Пока этого нет, формулировка «метаданные вырезаются, если остаётся исходный JPEG» слишком сильная.

## V02 — P2. Исправление пустого JSON сломало преобразование пробельного текста

**Новый регресс** относительно HEAD до работ. Код: [общий `TextConverter`](</home/gwer/code/qdbp/src/ui/TextConverter.tsx:33>).

`if (input.trim())` считает любой ввод из пробелов/табуляции/переносов отсутствующим и вообще не вызывает преобразователь. Для JSON пустое состояние уместно, но для кодирования такие символы — полноценные данные.

Подтверждено в браузере:

| Инструмент | Ввод | Ожидается | Факт |
|---|---|---|---|
| Base64, encode | Три пробела | `ICAg` | Пустой результат |
| URL encoder | Табуляция, пробел, перевод строки | `%09%20%0A` | Пустой результат |
| Смена регистра | Три пробела | Три сохранённых пробела | Пустой результат |

Затрагивается общий компонент, то есть проблема не ограничена RU. Тестирование конкретных трёх воспроизведений выполнено на RU; причина общая для локализаций.

Минимальное исправление: разделить «строка действительно пустая» и «для этого формата пробельный ввод равен отсутствию документа». Не отключать преобразование пробельных данных глобально ради JSON. Необязательно вводить новую инфраструктуру: поведение можно локализовать в JSON-компоненте.

Приёмка: три примера выше сохраняют значение; JSON при открытии остаётся без красной ошибки; обычный невалидный JSON всё ещё сообщает об ошибке; `aria-invalid` остаётся на исходном поле.

## V03 — P2. Добавление файла в 250-мс окно пересчёта оставляет его в «Обработка…»

Код: [отложенный пересчёт `ImageBatch`](</home/gwer/code/qdbp/src/ui/files/ImageBatch.tsx:93>).

Воспроизведение на `/ru/images/resize-image/`:

1. Загрузить `fixture.png`, дождаться результата.
2. Изменить ширину с 1280 на 400.
3. В течение 250 мс добавить второй файл — например, повторно тот же `fixture.png`.
4. Первый файл готов в размере 400×300; второй остаётся в «Обработка…» без скачивания. Состояние подтверждено после 1,5 с и ещё через 5 с; для этих небольших тестовых файлов это не нормальное время обработки.

[Скриншот](evidence/recheck/evidence/batch-stuck-after-add.png).

Причина: таймер замыкает старый `items`. По срабатывании он помечает **текущий полный список** как pending, но запускает `work(items, runId)` только для старого списка. У свежего файла прежний runId; его завершение либо отбрасывается, либо готовый статус уже перезаписан на pending.

Эта гонка видна и в версии компонента из исходного HEAD, поэтому я **не приписываю её появление нынешним изменениям**. Она обнаружена при приёмке обновлённой очереди и остаётся актуальной.

Минимальное исправление: пересчёт и очередь должны использовать один актуальный снимок списка/поколения задач. Нельзя переводить в pending файл, который не попадёт в новый прогон.

Приёмка: добавить файл до срабатывания таймера, во время обработки и сразу после неё — все строки должны закончиться результатом либо понятной ошибкой. Проверить также очистку и смену настроек. Желателен детерминированный тест с управляемым таймером, а не только ручная попытка попасть в интервал.

## V04 — P2. Лимит «не более двух файлов» действует на вызов, а не на компонент

**Статус F18: частично исправлен.** Код: [локальные воркеры `work`](</home/gwer/code/qdbp/src/ui/files/ImageBatch.tsx:66>) и [отдельный запуск из каждого `add`](</home/gwer/code/qdbp/src/ui/files/ImageBatch.tsx:86>).

В браузерной проверке `createImageBitmap` временно удерживается управляемым Promise. Это позволяет посчитать одновременно начатые декодирования без огромных пользовательских фотографий:

- Одно добавление четырёх файлов → одновременно 2: исправление для одного пакета работает.
- Два последовательных добавления по два файла, пока первые не завершились → одновременно **4**.
- Смена размера при двух незавершённых файлах → одновременно **4**: новый run запускается до завершения старых декодирований.

Это не замер падения вкладки и не стресс-тест на телефоне. Но общий предел, заявленный в комментарии и отчёте о работах, фактически не соблюдается; повторные добавления могут увеличивать число операций дальше.

Минимальное исправление: один счётчик занятых слотов/одна очередь на экземпляр `ImageBatch`, учитывающие добавления и смену поколения. Отбрасывание устаревшего результата не означает освобождения памяти ещё выполняющейся операции.

Приёмка: во всех трёх сценариях одновременно не более двух обработок; слот освобождается при успешном и ошибочном завершении; устаревшие результаты не возвращаются; новые файлы не остаются pending. Исправлять вместе с V03 — это одна область состояния, но два разных воспроизводимых отказа.

## V05 — P2. В мобильном поле основания системы счисления осталось 13,6 px

**Статус U06: в основном исправлен, один подтверждённый остаток.** Во всех пяти языках `/math/number-base/` поле `#nb-target` при ширине 375 px и `pointer: coarse` имеет computed `font-size: 13.6px`.

Код: [базовый `font: inherit` для `input[type=text]`](</home/gwer/code/qdbp/src/styles/global.css:217>), [новое мобильное правило](</home/gwer/code/qdbp/src/styles/global.css:570>), [поле внутри `.out-label`](</home/gwer/code/qdbp/src/pages/[lang]/math/number-base/_tool/NumberBase.tsx:60>).

Причина: `input[type='text']` специфичнее, чем мобильный селектор `input`, поэтому его `font: inherit` побеждает `font-size` из нового media query. В этом поле размер наследуется от `.out-label` с `0.85rem`.

[Скриншот](evidence/recheck/evidence/number-base-small-field.png). На остальных страницах в полном мобильном обходе полей ниже 16 px не найдено; `textarea.mono` теперь 16 px.

Минимальное исправление: мобильное правило той же или большей специфичности для текстовых полей. Приёмка — computed размер не меньше 16 px, в том числе у полей внутри уменьшенных подписей. Физический iOS Safari здесь не тестировался; утверждение относится к CSS и воспроизведённой эмуляции touch в Chrome, а не к реально измеренному iOS-zoom.

Новые URL работают, внутренние ссылки и hreflang не ведут на старые слаги. Но миграционные редиректы **не добавлены намеренно**: четыре проверенных старых адреса возвращают 404. Само отсутствие отправки сайта в Search Console не доказывает, что прежние URL никому не известны: роботы автоматически находят страницы. [Google о нахождении сайтов роботами](https://developers.google.com/crawling/docs/crawlers-fetchers/overview-google-crawlers), [рекомендации по переезду URL](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes).

Это отдельный принятый риск, а не ошибочная новая маршрутизация. Если прежняя production-версия уже доступна людям/роботам, минимальная страховка — точечные 301 для 49 адресов с сохранением query. Входа в Search Console, проверки индексирования и деплоя новой версии в рамках этой приёмки не было. Не утверждаю, что трафик уже потерян или что новые слаги уже находятся на production.

S01/S02/S03/S04/S07 и развитие из отчёта 06 — преимущественно планирование/осознанно отложенные функции; по ним не предполагается автоматическая реализация всего исходного списка. S05 — Lighthouse/CWV — здесь не измерялся. S06 на реальном хостинге заново не проверялся: отчёт `work/README.md` о production-поведении не подменяет независимый тест текущего деплоя.
