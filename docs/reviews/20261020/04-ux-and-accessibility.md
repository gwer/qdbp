# Десктоп, мобильный интерфейс и доступность

## Что уже хорошо

Страницы чистые, без визуального шума; инструмент стоит перед объяснениями. Числа результатов заметны, есть системная тёмная тема, логичные хлебные крошки, связанные инструменты и локализованные даты/единицы. Масштабируемость форм хорошая: полный обход 536 страниц при ширине 375 px и 96 RU-инструментов при 320 px не выявил горизонтального переполнения документа. Таблицы имеют собственную прокрутку; текстовый diff на узком экране переключается в единый список.

Это проверка в Chrome с эмуляцией viewport/touch, а не проверка физических iPhone/Android и всех экранных клавиатур. Доступность оценивалась по DOM/поведению и коду, без заявления о соответствии WCAG целиком.

## U01 — P2. Главная стала длиннее удобного каталога

На RU-главной 96 инструментов, 113 ссылок, высота около **15 193 CSS px** при ширине 375. На EN — 13 821 px. Поиска, навигации по разделам сверху и быстрых переходов к нужному инструменту нет. Пользователь, которому нужен EXIF или URL encoder, вынужден знать категорию или искать по странице.

Предлагается уже сейчас, не после 150 инструментов:

- клиентский поиск по названиям, синонимам и задачам с индексом отдельно для языка;
- компактные ссылки на 12 разделов и 6–10 популярных инструментов;
- «Все инструменты» как отдельный компактный каталог либо раскрывающиеся разделы;
- сохранение обычных HTML-ссылок: поиск дополняет доступный каталог.

Выдачу поиска строить вокруг задач: «сжать фото», «убрать GPS», «сколько дней», «убрать дубли». Запросы не отправлять на сервер. Не сохранять историю запросов по умолчанию.

## U02 — P2. Результат на телефоне слишком далеко от начала

На ипотеке при 375×812 виден основной платёж, а детали находятся ниже. На длинных формах пользователь должен прокручивать между вводом и результатом; длинные H1, описание и настройки занимают значимую часть экрана. При 320 px `.tool` некоторых страниц начинается примерно на 400–454 px от верха.

Сократить первый экран: компактный H1 без повторяющегося слова «онлайн», описание в одну-две полезные строки, ограничения раскрывать рядом с полем. Для длинных форм — компактный итог после группы полей или аккуратный закреплённый результат после первого успешного расчёта. Он не должен закрывать экранную клавиатуру и кнопки.

На десктопе текущая ширина 760 px удобна для статьи, но тесна для diff, JSON и сравнения таблиц. Разрешить расширенный рабочий блок для этих инструментов, сохранив читаемую ширину справки. Не растягивать все формы одинаково.

Скриншоты: [ипотека, 1440 px](evidence/mortgage-desktop-viewport.png), [ипотека, 375 px](evidence/mortgage-mobile-viewport.png).

## U03 — P2. Ошибки и пустые состояния требуют отдельного дизайна

Проблема F09 видна как блок результатов из прочерков без объяснения. JSON-форматтер сразу при открытии показывает «Ошибка в JSON: строка 1, столбец 1», хотя пользователь ещё ничего не вводил. Это воспроизводится на всех пяти языках.

Нужны разные состояния:

| Состояние | Что показывать |
|---|---|
| До ввода | Пример или короткая инструкция, без красной ошибки |
| Неполный ввод | Нейтральная подсказка; результат временно недоступен |
| Недопустимое значение | Конкретная причина у поля и способ исправления |
| Несовместимые поля | Предметное объяснение рядом с результатом |
| Долгая обработка | Прогресс/статус, кнопка отмены для тяжёлой операции |
| Ошибка обработки | Сообщение, повтор/удаление проблемного файла; старый ответ не выдаётся за новый |

При смене формата/качества в файловом инструменте старый `result` сохраняет кнопку скачивания, пока идёт перерасчёт. Предыдущий результат нужно обозначать или временно отключать скачивание, чтобы пользователь получил файл с выбранными настройками.

Скриншоты: [пустая форма JSON](evidence/dev-json-formatter--375-light.png), [безубыточность без объяснения](evidence/bug-silent-errors.png).

## U04 — P2. Ссылки и переключатели должны сохранять смысл задачи

F11: перевод единиц заменяет физические значения на другой пример. Это особенно опасно при сравнении результатов. F17: смена языка теряет введённое состояние. Пользователь должен понимать, что меняет представление, а что загружает другой пример.

Рекомендуемый набор действий: «Сбросить», «Загрузить пример», «Копировать результат», «Поделиться». Существующее сохранение расчёта в query оставить; «Поделиться» может копировать текущую ссылку по явному действию. При смене языка по возможности сохранять совместимые параметры расчёта. Содержимое загруженных файлов не включать в URL или clipboard автоматически.

У многих калькуляторов нет кнопки копирования результата, хотя у текстовых она уже есть. Для финансовых таблиц полезен CSV с пояснениями единиц и датой сценария; копирование и экспорт результатов запускать по действию пользователя.

## U05 — P2. Файловым инструментам нужны явные ограничения и управление пакетом

Работают выбор файлов, обработка и скачивание; HEIC реально декодируется в worker. Пользователю до выбора файла стоит показать поддерживаемые форматы и лимит 50 MB на файл, а для HEIC — 100 MP и размер дополнительной загрузки декодера.

Улучшения:

- удаление/повтор отдельного файла вместо только «Очистить всё»;
- ограниченный параллелизм обычных изображений, прогресс по пакету, отмена;
- указание, что будет с прозрачностью, EXIF, анимацией и Live Photo;
- предупреждение при увеличении размера и гарантия сохранения всех результатов в ZIP;
- сохранение ориентации/ICC объяснять пользовательскими последствиями, как уже сделано в EXIF.

Файловые операции проверены на синтетических 800×600 изображениях и реальном HEIC 1280×854. Проверка серии 48-MP снимков на телефоне ещё нужна. [HEIC после обработки](evidence/heic-mobile-viewport.png).

## U06 — P2. Проверить читаемость и масштабирование редактируемых полей на iOS

У `textarea.mono` размер **14,72 px**, у поля дополнительного основания в number-base — **13,6 px**. Это касается JSON/JWT/regex, Base64/hash/Morse/URL, UUID и части текстовых инструментов. Для редактируемых полей на мобильном стоит использовать минимум 16 px и отдельно проверить автоувеличение при фокусе в Safari. Реальный iOS в этом ревью не запускался, поэтому автоувеличение — риск совместимости, а не подтверждённая поломка.

Режимы имеют небольшие кнопки примерно 29 px высотой: для частых touch-действий удобнее 40–44 px. Не объявлять все такие кнопки нарушением WCAG: [минимум 2.5.8 — 24×24 px, с исключениями по отступам и контексту](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum). Большие touch-зоны — рекомендация удобства.

## U07 — P2. Связи ошибок с полями и уведомления о результате

Общий `Calculator` уже задаёт `aria-invalid`, `aria-describedby`, `aria-live`. Это хорошая основа. В `TextConverter` ошибка относится к исходному тексту, но `aria-invalid` ставится на read-only результат, а объяснение не связано с входом. Перенести связь на исходное поле. Для асинхронных операций обозначать busy/готовность без зачитывания длинных хешей каждую миллисекунду.

У breadcrumbs `aria-label="Breadcrumb"` жёстко английский во всех языках; локализовать. Скрытые native date inputs имеют `aria-hidden` и `tabIndex=-1`: найденные простым DOM-сканером отсутствующие label у них **не считать** дефектом доступного имени. UUID textarea имеет `aria-label` и тоже не является безымянным полем.

Нужно отдельное ручное прохождение клавиатурой и screen reader: фокус календаря, меню языков, таблицы, статусы обработки, сообщения при повреждённом файле. По одним атрибутам нельзя подтвердить удобство такого использования.

## U08 — P3. Визуальная полировка

- Выравнивать поля одной строки при многострочной подписи: на ипотеке «Первоначальный взнос» опускает input ниже соседнего. Можно задавать общее выравнивание по низу label.
- Карточка каталога выглядит кликабельной целиком, но ссылка находится только в заголовке; увеличить область перехода без вложенных конфликтующих ссылок.
- Сделать ручной переключатель светлой/тёмной темы, если это подтвердится запросами; системная тема уже работает.
- После основного блока оставить 3–6 действительно связанных инструментов и компактную ссылку на категорию. Сейчас «Ещё в разделе» повторяет почти весь раздел и сильно удлиняет мобильную страницу.
- На 404 объяснять проблему на языке префикса, давать поиск и ссылку на нужную главную; сейчас везде английское “Page not found.”

## Приоритет проверки после изменений

Сначала устранить скрытую порчу/передачу данных и предметные ошибки. Затем проверить три сквозных маршрута: найти инструмент → ввести свои данные → понять/скачать результат; исправить ошибку ввода → получить новый корректный результат; открыть на телефоне → сменить единицы/язык → сохранить тот же смысл задачи. После этого заниматься косметикой и новыми функциями.
