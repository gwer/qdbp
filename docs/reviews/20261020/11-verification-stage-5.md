## V06 — P2. Заполнение перед restart-маркером ломает новый JPEG-парсер

Код: [сканирование entropy-coded данных](</home/gwer/code/qdbp/src/ui/files/jpeg.ts:212>), затем [разбор длины следующего маркера](</home/gwer/code/qdbp/src/ui/files/jpeg.ts:209>).

Файл для воспроизведения: [progressive-filled-restart.jpg](evidence/recheck-v2/evidence/progressive-filled-restart.jpg). Это [обычный progressive JPEG](evidence/recheck-v2/evidence/progressive-restart.jpg), перед первым `FF D0` которого вставлен **один дополнительный `FF`**. Получается `FF FF D0`.

Такое заполнение допустимо: T.81, §B.1.1.2 разрешает байты `FF` перед любым маркером; §E.2.1 требует пропускать их при определении маркера. [Первичный стандарт JPEG, размещённый W3C](https://www.w3.org/Graphics/JPEG/itu-t81.pdf).

Независимое подтверждение: Chrome декодирует оба файла в 800×600, SHA-256 массива RGBA у них одинаковый:

`b893b4390aa800642c1072a91e707eb76ac3af520f5dcf979ff3ad5f80ca44e7`

Фактический результат:

| Способ проверки | Результат |
|---|---|
| Прямой `stripJpeg()` | Исключение `bad marker` |
| `/ru/images/compress-image/` | «Не удалось обработать файл», скачивания нет |
| `/ru/images/exif/` | Необработанная JS-ошибка `bad marker` во время рендера, результата и скачивания нет |

[Скриншот компрессора](evidence/recheck-v2/evidence/filled-restart-compress-image.png), [скриншот EXIF](evidence/recheck-v2/evidence/filled-restart-exif.png).

Причина: внутри скана проверяется только байт непосредственно после первого `FF`. Последовательность `FF FF D0` ошибочно объявляется концом скана. Внешний цикл пропускает заполнение и видит `D0`, но затем разбирает его как сегмент с длиной. У RST0–RST7 длины нет: следующие байты принадлежат сжатым данным, разбор теряет синхронизацию.

Минимальное направление исправления: при поиске конца скана сначала пройти все `FF` заполнения, затем классифицировать настоящий код маркера. RST0–RST7 должны оставаться частью скана вместе с заполнением. Обрабатывать их как сегменты с двухбайтовой длиной нельзя. Замена библиотеки или новая архитектура не требуется.

Приёмка:

1. Приложенный файл очищается обоими инструментами; скачанный результат декодируется с теми же пикселями.
2. Перед RST0–RST7 проверены варианты без заполнения, с одним и несколькими `FF`.
3. Текущие тесты экранирования `FF 00`, нескольких сканов, таблиц, удаления метаданных и обрезания хвоста остаются зелёными.
4. В EXIF нет необработанного исключения. Перехват ошибки сам по себе не заменяет поддержку корректного файла.

Приоритет P2: это более узкая совместимость, чем прежняя утечка метаданных. Распространённость таких файлов у реальных посетителей не измерялась. Не утверждаю, что сломан любой progressive JPEG: контрольный файл без дополнительного заполнения проходит.
