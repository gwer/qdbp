## Старые ссылки — основной сценарий принят

В браузере сравнены не только поля формы, но и результаты и таблицы старой ссылки с эквивалентным новым `prepay`:

- на всех пяти языках оба режима `term/payment`: `after=12&extra=10000&mode=…` равен `prepay=12:10000:…:once`;
- отсутствие `mode` даёт `term`; явный `after=0` сохраняется как корректный нулевой месяц;
- новый `prepay` выигрывает у старых параметров и для одной записи, и для списка с регулярными/разовыми погашениями;
- повреждённый новый `prepay=bad` не подменяется старым: ведёт себя как та же ссылка без старых параметров;
- явно присутствующий пустой `prepay=` тоже не включает старый fallback: поведение совпадает с обычной ссылкой `prepay=`;
- отсутствующие поля, дробный/отрицательный месяц, отрицательная/нулевая сумма, неправильный режим и `NaN` не переносятся.

На десяти сопоставлениях пяти языков страницы отвечают HTTP 200 **без редиректов**, canonical остаётся `https://qdbp.net/<lang>/finance/early-repayment/`. Слаги и `urls.txt` не менялись. Механизм `legacy` задокументирован; применение fallback только при отсутствии нового параметра реализовано в общем `readQuery()`.

Граница unit-покрытия: новый тест в `early.test.ts` называется в том числе «новый prepay важнее», но его assertions проверяют только `def.legacy()` и не проверяют общий `readQuery()`. Сейчас приоритет независимо подтверждён браузером. При добавлении будущего E2E-набора полезно закрепить там одновременное присутствие обоих форматов, без необходимости менять архитектуру ради этого теста.

## N03 · P3 · Не все повреждённые старые параметры отбрасываются

**Где:** `src/pages/[lang]/finance/early-repayment/_tool/tool.ts → legacy()`. Проверка сводится к `Number.isInteger(after) && after >= 0 && extra > 0` плюс наличию параметров и допустимому режиму. Наличие параметра не гарантирует непустую строку; положительность не гарантирует конечное число.

Для воспроизведения использовать `/ru/finance/early-repayment/?amount=100000&rate=10&months=120&…`:

| Старые параметры | Фактический результат |
|---|---|
| `after=&extra=10000` | Пустой месяц превращается в `0`; рассчитывается реальное погашение 10 000 ₽ сразу после выдачи, экономия **15 096,96 ₽** |
| `after=%20%20&extra=10000` | То же для строки из пробелов |
| `after=12&extra=Infinity` | В сумме появляется `∞`, ошибка у поля «Введите число» и общая «С такими значениями расчёт невозможен…», результата нет |
| `after=12&extra=1e309` | То же: переполнение преобразуется в `Infinity` |

**Ожидание в рамках заявленного контракта:** не переносить повреждённую старую запись, как уже делается для `NaN`, отрицательной суммы и неверного режима. Оставить стандартное состояние калькулятора для остальных параметров ссылки. Явный числовой `after=0` остаётся допустимым — замечание не про запрет нулевого месяца.

**Минимальное исправление:** до преобразования проверить, что строки `after` и `extra` непусты после `trim()`, затем дополнительно требовать `Number.isFinite(extra)`. Существующая проверка `Number.isInteger(after)` уже отсекает бесконечный месяц. Добавить четыре приведённых случая в тест, сохранив положительный пример `after=0`. Не нужны редиректы, изменение формата URL или новый интерфейс ошибок.

Это одна проблема валидации с четырьмя воспроизведениями, а не четыре отдельных дефекта. Приоритет низкий: нужны повреждённая/вручную составленная ссылка или ошибочный внешний генератор; нормальная форма такие ссылки не создаёт. Для бесконечной суммы страница не падает, а показывает управляемую ошибку. P01–P10, N01 и N02 этим не затронуты.

Доказательства: [чистые результаты](evidence/polish-final-20261021/legacy-pure.json), `browser.json → legacy-invalid-*`, снимки [пустого месяца](evidence/polish-final-20261021/screens/legacy-empty-month.png) и [бесконечной суммы](evidence/polish-final-20261021/screens/legacy-infinite-amount.png).
