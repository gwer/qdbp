# 03. Техническая реализация

> Ревизия 7 (2026-10-19): страница на категорию по той же схеме. Ревизия 6: стандартные острова Astro, страница на инструмент (`src/pages/[lang]/{category}/{tool}/index.astro` + `_tool/`). Ревизия 5: корень — 302, правила неполного покрытия языков, проверка внутренних ссылок. Ревизия 4: корень — редирект на /en/, строгие правила включения языков и `urls.txt`. Ревизия 3: английские слаги на всех языках (URL = путь к папке), упрощена модель инструмента, убраны реестр слагов, OG-генерация, FAQ-разметка, IndexNow, отслеживание устаревших переводов, валюты и прочие преждевременные вещи. Список убранного — в разделе 13.

## 1. Требования
- Только статика: никакого серверного кода в рантайме. Все вычисления на клиенте.
- Минимальный вес: HTML страницы инструмента < 50 КБ (gzip), JS типового калькулятора < 25 КБ (gzip) вместе с рантаймом, 0 КБ JS для статических страниц (каталог, категории, about).
- Core Web Vitals «зелёные» на мобильных даже с рекламой: LCP < 2,0 с, CLS < 0,05, INP < 150 мс.
- Новый типовой калькулятор — одна папка, 3–4 файла, без правок в «ядре».
- Сборка — до нескольких минут, dev-сервер мгновенный.
- Все проверки — одна локальная команда.

## 3. URL и структура каталога

### 3.1. Схема
```
/                                    302 → /en/
/{lang}/                             главная языка: категории + популярные инструменты
/{lang}/{category}/                  хаб категории
/{lang}/{category}/{tool}/           инструмент
/{lang}/about/, /privacy/, ...
```
Пример: `/ru/finance/loan-calculator/`, `/de/finance/loan-calculator/`.

- Категории и подгруппы образуют каталог: главная → категория → инструмент, хлебные крошки на каждой странице. Подгруппы внутри крупной категории — только разделы на странице хаба, не уровень URL.
- Все языки с префиксом, включая `/en/`.
- Корень: статический `302 / → /en/` в `public/_redirects` (Cloudflare применяет его раньше статических файлов). Для `astro dev`/`preview` тот же редирект продублирован в `astro.config.mjs` (`redirects`): локальные серверы `_redirects` не читают, а заглушка `dist/index.html` с meta refresh на проде не отдаётся. Именно 302, пока судьба корня не решена: 301 браузеры кешируют практически навсегда, и если потом в корне появится выбор языка или что-то ещё, у вернувшихся посетителей старый редирект продолжит срабатывать. Переход 302 → 301 делается в любой момент, обратный — нет. Цена 302: Google скорее оставит в индексе `/` (с содержимым `/en/`), а не `/en/` — для главной это нормально. `x-default` в hreflang указывает на `/en/`. Определение языка по `Accept-Language` не делаем: Googlebot ходит без него, а редирект по заголовку требует серверной логики. Посетителю с другим языком браузера на английской странице можно показать ненавязчивую ссылку «Есть версия на вашем языке» (клиентский JS, позже).
- Альтернатива — отдавать в корне английскую главную с `canonical` на `/en/`. Работает, но это дубль страницы и `canonical` для Google лишь подсказка; редирект проще и однозначнее.

### 3.2. Слаги — английские на всех языках
Решение: **слаги не локализуем**, `{category}` и `{tool}` — английские имена папок.

Почему:
- прямой вклад слов в URL в ранжирование Google очень мал; в выдаче вместо URL обычно показываются хлебные крошки (они локализованы);
- выигрыш (читаемость ссылок в мессенджерах, чуть больший вес URL в Яндексе) не окупает механику: перевод слагов, проверку уникальности, защиту от их случайной правки, редиректы;
- так делают многие крупные мультиязычные сайты.

Цена решения: **оно практически необратимо.** Перейти на локализованные слаги позже — это 301-редирект для всех страниц и несколько недель колебаний позиций. Если сомнения появятся, решать до запуска.

### 3.3. URL = путь к папке
С английскими слагами URL совпадает с путём в репозитории: `src/pages/[lang]/finance/loan-calculator/` → `/{lang}/finance/loan-calculator/`. Это обычная файловая маршрутизация Astro, без маппинга и реестра слагов.

Правило для всего `src/pages`: папка = URL, `index.astro` = страница, папка с `_` = данные (Astro не превращает файлы и папки с `_` в страницы). У каждого инструмента и каждой категории свой `index.astro`, одинаковый внутри своего вида (копируется как есть); всё своё лежит рядом в `_tool/` или `_category/`. Общий код страниц — в `layouts/ToolPage.astro` и `layouts/CategoryPage.astro`, данные — `toolPaths(def)` и `categoryPaths(def)` из каталога. Почему не один общий шаблон, — см. 5.3.

Переименование/перенос папки меняет URL — редирект добавляется руками строкой в `public/_redirects`. Пропустить это не получится: сработает проверка `urls.txt` (см. 6.1).

```
│              └─ content/{lang}.md  # как пользоваться, формула, примеры, FAQ

```

## 5. Модель инструмента

Два вида:

**Калькулятор** — движок пишется один раз, инструмент описывается конфигом:
```ts
// src/pages/[lang]/finance/loan-calculator/_tool/tool.ts
import { defineCalculator } from '@/ui/define';
import { island } from '@/ui/ToolRoot';
import { Schedule } from './Schedule';           // необязательно: свой блок результата

export const def = defineCalculator({
  related: ['mortgage-calculator', 'compound-interest'],
  inputs: {
    amount: { type: 'number', default: 1_000_000 },
    rate:   { type: 'percent', default: 12 },
    months: { type: 'integer', default: 60 },
    kind:   { type: 'select', options: ['annuity', 'differentiated'], default: 'annuity' },
  },
  compute: (v) => loan(v),                         // чистая функция, покрыта тестами
  outputs: { payment: 'number', overpay: 'number' }, // простые значения — движок рисует сам
  Extra: Schedule,                                 // таблица/график/иллюстрация — обычный Preact-компонент
});

export default island(def);                        // компонент-остров для index.astro
```
- Длительность с `seconds: true` — «ч:мм:сс» / «мм:сс», значение в секундах (забеги, темп).
- `custom`-результат получает `FormatContext` (`t`, `lang`, `units`, `clock`) — может показывать значение в единицах выбранной системы.
- После конвертации единиц поле показывает округлённое число, но пока пользователь его не правил, расчёт и URL используют точное значение (карта `exact` в `Calculator.tsx`) — переключение систем не накапливает погрешность.
- Значение по умолчанию может зависеть от языка: `byLang: { ru: 22, de: 19 }` у number/percent/integer/quantity/select (ставка НДС страны, привычный формат, правдоподобные суммы). Для select сборка проверяет, что значение есть в `options`.
- Типы полей — по мере надобности. Есть: number, integer, percent, select, date (своё текстовое поле `src/ui/DateField.tsx` в записи языка — 19.10.2026, 10/19/2026, 19/10/2026; порядок и разделитель — из `Intl`, разбор и запись — `src/lib/date-input.ts`; кнопка в поле открывает нативный календарь через скрытый `<input type="date">` и `showPicker()` — календарь можно заменить своим в одном месте; значение `YYYY-MM-DD`, в URL тоже; default — `YYYY-MM-DD`, `today`/`today±N` или `next-MM-DD`, относительные подставляются только в браузере), duration («ч:мм», значение в минутах), time (время на часах — своё текстовое поле, не нативный `<input type="time">`, чей формат 12/24 ч диктует система; формат выбирает пользователь переключателем над формой, по умолчанию по языку, выбор хранится в `localStorage` и применяется и к результатам; принимает «22:30», «9.30», «9,30», «9»; в URL — всегда `HH:MM` 24 ч; default `HH:MM` или `now`). Типы результатов: числа (number/integer/money/percent), date, datetime (мс; местный пояс или UTC), duration, clock (время на часах в записи языка: «01:30» / «1:30 AM»), text и custom — своя функция `format(value, { t, lang })`, когда нужны строки перевода (например, «через 2 дня» с правильным множественным числом). Даты — утилиты `src/lib/date.ts`.
- Простые значения результата движок выводит сам. Всё сложнее (таблица платежей, график, SVG-схема фигуры) — обычный Preact-компонент в `Extra`, получающий результат `compute`. Отдельного декларативного языка для таблиц и графиков не делаем; общие `<Table>` и `<Chart>` появятся как компоненты, когда понадобятся во второй-третий раз.
- Пересчёт на каждый ввод, без кнопки.
- Состояние в query (`?amount=…`) — делиться ссылкой; canonical без параметров. Это ~20 строк в движке.
- Поля — `type="text"` + `inputmode="decimal"`, парсер принимает `,` и `.` (у `type="number"` разное поведение с запятой в разных браузерах).

**Свой компонент** — для обработки файлов, таймеров, текстовых инструментов: `export const def = defineTool({ component })` + `export default island(def)`; компонент собирается из тех же полей и карточек.

Обязательно у любого инструмента: `i18n/{lang}.json`, `content/{lang}.md`, тест для всего, что считает.

### 5.3. Как работает гидратация
Используются стандартные острова Astro: в `index.astro` инструмента — `<Tool client:load {...island} />`.

- `def` (определение с функциями: `compute`, компоненты) живёт внутри модуля `_tool/tool.ts`. В остров уходят только сериализуемые пропсы: язык и строки перевода. Поэтому `export default island(def)` — маленькая обёртка, которая замыкает `def` внутри компонента.
- Astro требует, чтобы гидратируемый компонент был импортирован в шаблоне статически: выбрать его динамически в одном общем шаблоне нельзя (проверено: ошибка `NoMatchingImport`). Отсюда страница на инструмент вместо одного `[tool].astro`. Общий код страницы — в `layouts/ToolPage.astro`, данные для неё — `toolPaths(def)` из каталога.
- Каталог проверяет, что у каждого `_tool/tool.ts` и `_category/category.ts` есть `index.astro` и наоборот.
- Категории устроены так же (хотя острова у них нет), чтобы во всём `src/pages` была одна модель и не было перекрытия статических папок с динамическим маршрутом.

Ранее была своя гидратация через общий скрипт с ленивой картой инструментов; заменена на стандартные острова, чтобы не держать нестандартную механику. По запросам и весу разница несущественная (замерено в браузере).

Вес на странице (gzip): Preact ~4,4 КБ + клиент-рендерер Astro ~1,5 КБ + общий движок ~2,6 КБ + хуки ~1,2 КБ + чанк инструмента (процент — 0,2 КБ, кредит с `decimal.js-light` — 6,7 КБ). Страница кредитного калькулятора целиком — ~16–17 КБ JS, 5 запросов; все, кроме чанка инструмента, общие для всех страниц и кешируются.

Известное ограничение: если пользователь начнёт вводить до загрузки JS (медленная сеть), введённое до гидратации может потеряться. Решать, если увидим проблему в реальных данных.

## 6. i18n

### 6.1. Строки и контент
- Общие строки — `src/i18n/{lang}.json`, строки инструмента — рядом с ним, длинный текст — Markdown.
- Своя `t()` с интерполяцией и плюрализацией на `Intl.PluralRules` (~30–50 строк).
- Язык у инструмента включён, если в его папке есть файлы этого языка. Отдельных флагов нет. Чтобы ничего не терялось по ошибке, сборка строгая:

  | Ситуация | Что происходит |
  |---|---|
  | Есть `i18n/ru.json`, но нет `content/ru.md` (или наоборот) | Ошибка сборки |
  | Файл с неизвестным кодом языка (`pt-br.json` вместо `pt.json`, опечатка `ru.josn`) | Ошибка сборки |
  | У инструмента нет ни одного языка | Ошибка сборки |
  | В JSON нет обязательного ключа: `title`, `description`, подпись каждого поля и результата из `tool.ts` | Ошибка сборки |
  | Наборы ключей в языковых файлах одного инструмента различаются | Ошибка сборки |
  | Язык удалили / папку переименовали / перенесли — страница пропала | Ошибка сборки через `urls.txt` (ниже) |
  | У инструмента просто ещё нет перевода | Норма; видно в отчёте покрытия |

- **`urls.txt`** — отсортированный список всех URL сайта, закоммичен в репозиторий. После сборки скрипт сравнивает его с тем, что реально собралось:
  - URL пропал и на него нет редиректа в `_redirects` → ошибка (самая дорогая ошибка — молча потерять проиндексированную страницу);
  - появились новые URL → ошибка с подсказкой выполнить `pnpm urls:update`, который перезаписывает файл.

  Так каждое добавление и удаление страниц явно видно в диффе коммита. Это ~25 строк скрипта; полезнее, чем казалось при отказе от локализованных слагов: защищает не от правки слагов, а от удаления файлов.
- **Отчёт покрытия** — тот же скрипт печатает сводку «язык: N из M инструментов» и список инструментов без перевода на включённые языки. Ничего не валит, просто показывает пробелы.

### 6.2. Неполное покрытие языков
Инструмент может быть не на всех языках — это нормальная ситуация, а не временный дефект.

**Когда неполнота полезна:**
- **Локальные инструменты.** Проверка ИНН нужна на русском, NIF — на испанском, немецкий Brutto-Netto — на немецком. Перевод ИНН-валидатора на японский — страница без спроса и без ценности, ровно то, что Google считает масштабированным малоценным контентом. Английский у таких инструментов не обязателен (иногда полезен: иностранцы, разработчики — решаем по спросу).
- **Нет спроса на языке.** Калибр проводов AWG почти не ищут по-русски, налоговые калькуляторы конкретной страны — на чужих языках. Страница без показов только тратит краулинговый бюджет и попадает в «Просканировано, но не проиндексировано», что тянет вниз оценку качества сайта целиком.
- **Постепенный перевод.** Сначала переводим то, что уже доказало спрос (по Search Console исходного языка), а не всё подряд.
- **Качество.** Финансы и здоровье публикуем на языке только после вычитки. Лучше без языка, чем с плохим переводом.

**Что из-за неполноты нужно учесть** (всё решается тем, что любые списки и ссылки строятся из одного источника — языков, реально имеющихся у инструмента):
- **hreflang:** у каждой страницы перечисляются только существующие версии + `x-default` на английскую, если она есть. Если у инструмента один язык — hreflang не выводится вовсе. Согласованность получается по построению.
- **Sitemap:** только существующие страницы. Альтернативные версии в sitemap не дублируем — hreflang живёт только в `<head>`, этого достаточно.
- **Переключатель языка на странице инструмента:** показывает только языки, на которых есть эта страница. Не ведём на главную другого языка — это вводит в заблуждение.
- **Хабы категорий, главная, «похожие»:** на языке X показываем только инструменты, существующие на X. Категория без инструментов на языке X не генерируется и не показывается в навигации X.
- **Ссылки внутри Markdown-контента** (автор вручную сослался на другой инструмент) — могут вести на непереведённую страницу. Ловится проверкой внутренних ссылок (раздел 10).
- **Порог открытия языка:** язык появляется на сайте (главная, переключатель), только когда на нём есть хотя бы ~20–30 инструментов. Иначе язык выглядит пустым и для пользователя, и для Google. До порога его страницы просто не собираются (список языков сайта — в конфиге `src/i18n`).
- Для LLM-перевода — один файл глоссария на язык, просто как часть промпта.

### 6.3. Поддержка Intl в браузерах
| API | Статус | Решение |
|---|---|---|
| `NumberFormat`, `DateTimeFormat`, `PluralRules`, `RelativeTimeFormat` | Везде давно (PluralRules — Safari 13+, 2019) | Используем |
| `NumberFormat` со `style: 'unit'` | Safari 14.1+ | Используем |
| `Intl.Segmenter` | Все движки, Firefox с 2024 | Используем (счётчик слов) |
| `Intl.DurationFormat` | Во всех движках только с 2025 | Не используем; длительности — через `PluralRules` |
| `Temporal` | Chrome 144+, Firefox 139+; в стабильном Safari нет | Не используем; даты — `Date` в UTC через утилиты `lib/date` |

### 6.4. Intl при пререндере vs в браузере
- Всё форматирование — через одну обёртку `lib/format.ts`, которая нормализует пробелы (U+202F/U+2009 → U+00A0) — это убирает основные расхождения между Node и браузерами.
- После гидратации результат пересчитывается в браузере — пользователь видит клиентское форматирование, разметка та же.
- Ничего, зависящего от «сейчас», не считается при сборке: «сегодня» подставляется на клиенте. Сборка с `TZ=UTC`.

### 6.5. Единицы измерения (реализовано)
- Поле `type: 'quantity'`: `unit` — метрическая единица инструмента, `imperial` — её аналог для американской системы (`m`↔`ft`, `cm`↔`in`, `l`↔`gal`, `m3`↔`yd3`, `kg`↔`lb`, `m2_per_l`↔`ft2_per_gal` и др., см. `src/lib/units.ts`), `default` — в `unit`, `defaultImperial` — «круглое» значение для американской системы. Результат `type: 'quantity'` — так же, с обозначением единицы.
- `compute` всегда получает значение в `unit` — формулы не зависят от системы. В URL — тоже в `unit`.
- Переключатель «Единицы: метрические / американские» появляется над формой, если у инструмента есть поле или результат с `imperial`. По умолчанию — по языку (en — американские), выбор хранится в `localStorage` на весь сайт; сохраняется только изменённая настройка.
- При переключении поле со значением по умолчанию получает значение по умолчанию новой системы, введённое пользователем — конвертируется с округлением до сотых.
- Поля в дюймах в американской системе принимают и запись «5'10\"».
- Обозначения единиц — по языку (`unitSymbol`): «м²» в ru, «sq ft» в en, «ft²» в остальных.
- Метки полей с величинами пишутся **без единиц** («Вес», а не «Вес, кг») — единицу показывает суффикс поля.

### 6.6. Валюты
Не делаем. Денежные поля — просто числа с группировкой разрядов по локали, без символа валюты. Калькулятору кредита валюта не нужна.

## 7. SEO
- Уникальные `<title>` и `description` из i18n инструмента. `title` — существительное-название инструмента, при необходимости с уточнением после двоеточия («Калькулятор дней: сколько дней между датами»); часть до двоеточия — короткое имя для хлебных крошек и списков (`toolName`).
- `canonical` на себя, без query.
- `hreflang` + `x-default` только в `<head>`, генерируются из списка языков, реально имеющихся у страницы (см. 6.2).
- Sitemap — `@astrojs/sitemap`, простой список URL, без alternate-ссылок и `lastmod`.
- JSON-LD: `WebApplication` и `BreadcrumbList`. `FAQPage` не используем — с 2023 года Google показывает FAQ-сниппеты только авторитетным сайтам о здоровье и госорганам.
- OG-картинки: одна статическая на сайт (позже — на категорию). Генерация на каждую страницу не нужна.
- Хлебные крошки, «похожие» (из `related`), «ещё в категории».
- Структура страницы: H1 → инструмент выше сгиба → результат → пояснение → формула → примеры → FAQ → связанные.
- `robots.txt`, 404 на каждом языке.

## 8. Производительность
- Системные шрифты, inline SVG-иконки.
- Рантайм Preact + общие компоненты — один кешируемый чанк; код инструмента — отдельный.
- Тяжёлые зависимости (WASM-кодеки, pdf-lib): на странице инструмента начинаем `import()` в фоне после `load` + `requestIdleCallback`, если не включён `saveData`. Если пользователь выбрал файл раньше — показываем «Подготовка…» и ждём тот же промис. Совсем тяжёлое (модели в десятки МБ) — только по клику.
- `_headers`: immutable для хешированных ассетов.

## 9. Реклама и аналитика

### 9.1. Реклама
- `<AdSlot>` резервирует место заранее → нет сдвигов вёрстки.
- Рекламный скрипт — после `load` + idle.
- Сертифицированная Google CMP для EEA/UK/CH — при подключении рекламы (в AdSense есть бесплатная).
- Никакой рекламы между вводом и результатом.
- `ads.txt`.

### 9.2. Аналитика
Только бесплатные встроенные инструменты; сторонние счётчики (GA4, Метрика и т. п.) не ставим: они тяжёлые (десятки КБ JS), ставят cookies и требуют согласия пользователя.

| Вопрос | Источник |
|---|---|
| По каким запросам нас находят, показы, CTR, позиции, индексация | **Google Search Console** (хранит 16 месяцев), Bing Webmaster Tools, Яндекс Вебмастер — бесплатно, без кода на сайте |
| Сколько посетителей, какие страницы, откуда пришли, страны, устройства, браузеры | **Cloudflare Web Analytics** |
| Реальные Core Web Vitals по страницам | Cloudflare Web Analytics (LCP, INP, CLS у реальных пользователей) + отчёт CWV в Search Console |
| Доход по страницам, странам, языкам | Кабинет рекламной сети |

**Cloudflare Web Analytics** — встроенная в Cloudflare, бесплатная, без cookies (поэтому не нужен баннер согласия). Для сайта на домене, который обслуживает Cloudflare, включается в дашборде одной кнопкой: скрипт-маячок (несколько КБ) Cloudflare вставляет в страницы сам, в код ничего добавлять не нужно. Можно и вручную вставить `<script>` в Layout — тогда он под нашим контролем (например, грузить после `load`).

Ограничения, которые надо понимать:
- **нет своих событий** — нельзя узнать, сколько людей реально что-то посчитали или обработали файл, есть только просмотры страниц;
- **на длинных периодах данные сэмплируются** (оценка по выборке) — для трендов годится, для точных цифр нет;
- **хранение — около 6 месяцев**; долгую историю даёт Search Console (16 месяцев) и кабинет рекламы;
- Core Web Vitals собираются только в Chromium-браузерах.

Для старта этого достаточно. Если позже понадобится считать использование инструментов (какие инструменты реально используют, а не просто открывают), варианты:
1. **Workers Analytics Engine** — тоже встроенный в Cloudflare: маленький обработчик `/e` в том же Worker, который отдаёт статику, пишет события из `navigator.sendBeacon`. Это минимальная серверная часть только для аналитики (сами инструменты остаются клиентскими). Лимиты бесплатного плана проверить перед внедрением.
2. Не делать: косвенные сигналы (время на странице, доля повторных визитов, клики в Search Console) часто дают достаточно.

## 10. Проверки и деплой
`pnpm check` = `tsc --noEmit` + `vitest run` + `astro build` + один скрипт пост-проверок `dist/`: сверка с `urls.txt`, проверка внутренних ссылок (каждый `href="/…"` в собранном HTML указывает на существующий файл в `dist/`), отчёт покрытия переводов, бюджеты размера (gzip-вес JS/HTML против лимитов из раздела 1). Всё вместе — до сотни строк. Полнота и корректность файлов переводов проверяется самой сборкой.

Деплой: Cloudflare Workers Builds подключён к приватному GitHub-репозиторию, команда сборки — `pnpm check`; упала проверка — деплоя нет. Ветки → превью, `main` → прод. Бесплатно: 3 000 минут сборки в месяц. Lighthouse — вручную, при изменении шаблонов.

Объём файлов: без OG-картинок на каждую страницу даже 500 инструментов × 15 языков ≈ 7,5 тыс. HTML + ассеты — в пределах бесплатного лимита Cloudflare (20 000 файлов). Платный план ($5/мес, 100 000 файлов) — когда приблизимся.

## 11. Меняющиеся данные — избегаем
- Не делаем инструменты на данных, которые устаревают чаще раза в год (курсы валют, ставка ЦБ «на сегодня», CPI). Если ставка/курс нужны для расчёта — это поле ввода.
- Праздники и календари считаются кодом (`date-holidays`, Intl).
- Редкие исключения (ставки НДС, размеры одежды) — статический JSON рядом с инструментом и строка «Данные актуальны на …» в тексте страницы.

## 13. Что сознательно НЕ делаем (и почему)
| Не делаем | Почему / когда вернуться |
|---|---|
| Локализованные слаги | Мало пользы, много механики (см. 3.2) |
| Реестр слагов, автогенерация редиректов | URL = путь к папке; редиректы редки, пишутся руками (а забыть их не даёт `urls.txt`) |
| Декларативные таблицы/графики в конфиге | Обычные компоненты проще; общие `<Table>`/`<Chart>` — при повторном использовании |
| OG-картинки на каждую страницу | Мало влияют на трафик tool-сайта, удваивают файлы и время сборки |
| `FAQPage`-разметка | Google её больше не показывает для таких сайтов |
| IndexNow, `lastmod` из git | Хватает sitemap; git-история в облачной сборке может быть неполной |
| Отслеживание устаревших переводов, статусы перевода | `git log` по файлу; вернуться при 5+ языках и регулярных правках |
| Валюты, переопределение единиц у поля, автоопределение региона | Нет потребности на старте |
| Поиск по сайту | После 150+ инструментов |
| CMS, SSR, монорепа, Lighthouse CI, отдельный CI | Не нужны для статики одного разработчика |
| Аккаунты, серверное хранилище | Избранное/выбор единиц — `localStorage` |
| Инструменты на часто меняющихся данных | Нет ресурса их поддерживать |
| Signals, Playwright, Service Worker, PWA | По мере реальной потребности |
